# 大规模测试输入与模型配置

## 大输入的处理范围

正式输入文件支持最多 4 MiB；全部应用文件合计最多 8 MiB。输出、标程、验证器和模板等代码文件仍各限 256 KiB。可信生成器的回放伴随文件 `generator-data.b64` 是数据文件，限 4 MiB，并计入总量。

正式 Python 生成器的 JSON 输出通过 go-judge 缓存文件读取，最大 8 MiB；读取后立即尽力删除已返回的缓存。超限、无效 JSON、执行失败或取消都不会把部分输入当作完整结果。普通程序 stdout 及压力生成器仍保持原有限制；60 组压力数据、独立验证、validator、模板和区分度验证不减少。

可信 GeneratorPlan 单集合支持最多 200000 个元素，所有 CASE 的生成工作量合计仍限 1000000。大回放数据不能压进小脚本时，下载或保存 `generator.py` 和 `generator-data.b64`，置于同一目录后运行。伴随文件保存原始 base64 数据，不添加代码注释。

生成结果继续保存在任务中供教师预览。应用时，未编辑的文件按已授权任务中的文件名引用；改过的文件提交教师的实际内容。当 JSON 转义会使请求超过 Hydro 的 8 MiB JSON 限制时，前端自动使用原始文件上传，服务端仍逐个检查权限、类型、UTF-8、规范化后的大小及总量。任务引用不允许读取其他用户、其他题目或未完成任务的文件。

这些限制是资源预算，不是题面约束。必要覆盖仍超过预算时，系统应明确要求人工复核，不能截断输入、删除测试点或把缩小必要规模算作完成。完整验证与答案抽查分别报告；传输成功并不意味着题目算法正确。旧 v5 及更早提示词检查点需要重新生成，已生成或应用的数据不迁移。

缓存接口依据 [go-judge 官方 API](https://docs.goj.ac/api)；Hydro 的请求体和上传生命周期依据项目所用 `@hydrooj/framework/server.ts` 实现核对。

## 如何帮助管理员选择模型

分工指不同角色可以调用不同模型；没有单独设置的角色继承测试数据生成场景的模型链。当前管理页支持六个角色的独立模型链，本次大输入改动不改变配置界面或默认模型。

| 角色 | 选择依据 |
| --- | --- |
| 题意主提取 | 能准确提取约束、样例和输入编码，并稳定返回结构化内容 |
| 标程 | 编程与算法能力，尤其是最大规模的正确性和复杂度 |
| 题意复核、独立验证 | 能发现遗漏与反例；与被复核方使用可区分的模型身份 |
| 外围制品 | 输入协议、模板和有界生成的稳定性；通过测试后再比较速度与费用 |
| 分歧裁决 | 能依据题面证据判断冲突，而非简单投票 |

建议后续产品把基本配置收敛为“主模型”和“独立验证模型”，其余角色默认继承相应配置；六角色和备用链保留为进阶设置。界面检查应包含实际生效的继承链、端点可用性和当前可检测的模型身份冲突。不同名称或端点不保证底层模型真的独立，因此只能说明可验证的配置事实。

推荐配置需要标明测试日期、端点、模型版本、题型、样本量、产物检查通过率、完整验证通过率及成功任务耗时。一次最小请求只能证明端点可调用，不能证明算法能力；失败提前结束不能记作提速。只在有足够同题重复测试后提供“已验证推荐”，未测试的组合明确标为“自定义、未验证”。

本次此前的 Pro/Flash/Sonnet 分工实验只有求和产物通过外部检查，另外三题失败，且求和仍未通过完整验证。因此它是候选方案，不能直接设为面向用户的默认推荐。本次未修改在线模型配置。
